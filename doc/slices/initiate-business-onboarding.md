# Initiate business onboarding

## Purpose

Start a business onboarding process for an authenticated Tooyioo user who has completed user onboarding.

## Endpoint

`POST /business-onboarding/initiate`

The endpoint requires the `UserOnboarded` authorization policy, so the authenticated principal must contain the app-owned `user_id` claim.

## Inputs

The request body contains:

- `legalName`, required

The authenticated principal supplies the initiating user through its `user_id` claim. The slice does not read provider-specific identity claims.

## Streams and events

The business onboarding process stream receives:

- `BusinessOnboardingInitiated`

The event contains:

- `LegalName` from the request
- `InitiatedBy` from the authenticated principal's `user_id`

## Idempotency

The slice generates a new business onboarding id for each request and does not claim a business or user identity. Repeating the command creates another business onboarding process.

## Consistency

The handler appends to a single process stream with the expected stream version from the loaded state.

If another request appends to the same stream between load and append, Eventuous raises an optimistic concurrency exception and the slice returns a conflict result.

## Decisions

- Business onboarding is initiated only by already onboarded users, because the process belongs to a Tooyioo user.
- `InitiatedBy` records the app-owned user id, not a Google-specific claim.
- The business onboarding id is generated by the command mapper, following the initiate user onboarding slice.
- Initiation writes only the business onboarding process stream. The current domain events define no separate claiming stream for business onboarding.

## Open questions

- Whether a user may have multiple concurrent business onboardings.
- Whether initiation should be idempotent per user or per business once a uniqueness rule exists.
